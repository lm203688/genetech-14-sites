# 采集频率与额度预算测算

> 结论先行：**数据采集频率定为 30 分钟一次（`*/30 * * * *`）**，不是 5 分钟。
> 提速靠「单轮抓得深」（limit=150 + 游标分页），不靠「抓得勤」。
> 最后测算：2026-08-05

---

## 一、为什么 5 分钟不可行

单轮请求量（14 站 × 每站约 7 个检索词）：

| 数据源 | 每轮请求数 | 说明 |
|---|---|---|
| OpenAlex | 98 | 每词 1 次 |
| arXiv | 98 | 每词 1 次 |
| Crossref | 98 | 每词 1 次 |
| PubMed | 196 | esearch + esummary 各 1 次 |
| **合计** | **490 / 轮** | |

不同频率下的日请求量与各源限流线对比：

| 频率 | 轮次/天 | 总请求/天 | OpenAlex（10万/天） | arXiv（≥3s/次） | PubMed（3 req/s 无 key） |
|---|---|---|---|---|---|
| `*/5` | 288 | 141,120 | 28,224（28%）勉强 | **28,224 ❌ 必封 IP** | **56,448 ❌ NCBI 封禁** |
| `*/15` | 96 | 47,040 | 9,408（9%）✅ | 9,408 ⚠️ 偏高 | 18,816 ⚠️ 偏高 |
| **`*/30`（采用）** | **48** | **23,520** | **4,704（4.7%）✅** | **4,704 ✅** | **9,408 ✅** |
| `0 */2` | 12 | 5,880 | 1,176 ✅ | 1,176 ✅ | 2,352 ✅ |

**红线说明**
- **arXiv**：官方 API 使用条款要求请求间隔 ≥ 3 秒，且不欢迎持续高频轮询；批量获取应走 OAI-PMH。`*/5` 下同一 UA/IP 每天 2.8 万次并发 burst，会被 403 直至封禁。这是最硬的一条红线。
- **PubMed E-utilities**：无 API key 限 3 req/s，NCBI 对滥用者先发邮件警告后封 IP，并建议大批量任务放在美东夜间。
- **OpenAlex**：带 `mailto` 进入礼貌池，约 10 万次/天、10 req/s，是四个源里最宽松的。
- **Crossref**：礼貌池无硬性日上限，但滥用会被降级到公共池（响应显著变慢）。

## 二、关键判断：高频的边际收益接近零

学术数据库（OpenAlex / arXiv / Crossref / PubMed）的**索引更新是「天」级**的。
同一组检索词每 5 分钟查一次，返回的是同一批结果，经 `seen` 去重后**新增实体≈0**——
只消耗额度，不增加数据。

**真正决定建库速度的是单轮抓取深度**，即 `--limit` 与分页游标：

| 配置 | 单轮理论上限 | 日请求量 |
|---|---|---|
| `*/5` + limit=30 | 420 实体 | 141,120（超限）|
| **`*/30` + limit=150** | **2,100 实体** | **23,520（安全）** |

单轮产出提升 **5 倍**，总请求量下降 **83%**。

## 三、Cloudflare Pages 构建额度（最容易爆的账号级共享额度）

本账号下 **5 个项目共用同一个 Cloudflare 账号**：
`知识引擎14站` / `aishield` / `healthlens` / `robopart` / `swarmlabs`

Cloudflare Pages 免费版 **500 builds/月，账号级共享**。超出后**当月所有项目部署全部停止**。

若 48 次/天的采集每次都 push 触发构建 → **1,440 builds/月**，直接拖垮全部项目。

**已实施的守门策略**（`ops.yml` → `Commit data updates`）：
- 数据照常入库（每轮都 commit + push）；
- 仅当「本轮新增 ≥ 60 条」**或**「距上次发布 ≥ 4 小时」时，才发出触发构建的提交；
- 其余提交在 message 中打 `[CI Skip]` 标记，Cloudflare Pages 自动跳过构建。

预算结果：**≤ 6 builds/天 ≈ 180 builds/月**，为其余 4 个项目留出 320 次余量。

## 四、GitHub Actions 运行次数总账（账号级）

盘点本机所有项目的定时任务：

| 项目 | 工作流数（含 cron） | 频率 | 运行次数/天 |
|---|---|---|---|
| **aishield** | 12 | `*/20` | **864** |
| 知识引擎14站 | 1 | `*/30` | 48（原 `*/5` 为 288）|
| healthlens | 2 | `*/30` | 96 |
| swarmlabs | 2 | 每日 2 次 | 4 |
| robopart | 0（仅 push 触发）| — | 0 |
| **合计** | | | **约 1,012 次/天** |

- 若仓库为 **public**：Actions 分钟数免费无限，但受**并发 job 上限**（Free 账号 20）与
  **GitHub 高负载时定时任务被延迟/丢弃**影响，`*/5` 这类高频 cron 实际经常不按点触发。
- 若仓库为 **private**：Free 额度 2,000 分钟/月。按均次 2.5 分钟计，
  1,012 次/天 ≈ **75,900 分钟/月**，超额 **37 倍**。

**最大消耗方是 aishield（864 次/天，占 85%）**，12 个工作流全部设为 `*/20`。
建议错峰并分级降频（详见下方建议）。

## 五、推荐配置

| 任务类型 | 推荐频率 | 理由 |
|---|---|---|
| 学术数据采集 | **30 分钟**（提升期）/ 每日 1-2 次（常态）| 源更新为天级，30 分钟已远超实际需要 |
| 部署保活 / 健康检查 | 每日 1 次 | 无状态变化，高频无意义 |
| 安全扫描 / 依赖巡检 | 每周 1-2 次 | 变更驱动，非时间驱动 |
| 推广 / 分发 | 每日 1 次 | 外部平台本身有频控 |

**通用原则**
1. 时间驱动的任务里，真正需要高频的只有「数据采集」，且 30 分钟是性价比拐点。
2. 高频任务必须配额度守门（跳过无变更、跳过构建、攒批发布）。
3. 多项目共用账号时，额度是**抢占式共享**——任何一个项目失控都会拖垮其余全部。
4. 分钟数错开（`7 */4`、`23 */6`）避免整点撞车导致并发排队。

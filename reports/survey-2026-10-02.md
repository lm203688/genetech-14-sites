## 0. 一句话结论

**数据资产是真的（30 万实体 / 可追溯来源 / 9 个 API 端点全活），但工程与商业的两端都还没通：**
每日 CI 有一个工作流连续三天红、知识图谱被自己的护栏自锁、语义检索只覆盖 6% 且卡在架构上限、
消费者接入文档与定价未闭环。本轮已修掉两个会静默烧掉整轮 CI 的真 bug，并补齐了 API 规范与接入文档；
真正剩下的硬骨头只有三块：引用图谱、语义检索的架构突破、以及付费闭环。

## 3. 科研方向（三条，都有本项目已有数据支撑，不是空谈）

### 方向一：跨站引用缺口检测（Cross-site Citation Gap Detection）

**命题**：把引用网络用于**学科能力缺口定位**，而非文献计量学传统的共引/共词分析。

**现有条件**：语料含 **260,689 个唯一合法 DOI**（另有 23,231 条无 DOI 实体），
引用边正在用 `pipeline-openalex-citation.js` 抓取（select `referenced_works`）。
设计上只保留 **source/target 分属不同站点** 的边，域内引用只计数不算边——
这恰好把研究目标收敛到「跨域」上，与 30 站跨学科定位天然对齐。

**方法**：对站对 (A, B) 定义缺口分数
`gap(A→B) = 引用密度(A→B) × 成熟度差 × 主题距离`，
其中成熟度可用 `cited_by_count` _year 分布刻画。留一站点做验证：
被预测为「有缺口」的站对，其后续 6 个月是否真的出现了跨站工程/方法成果。

**可发表的点**：现有文献把引用图用于「学科结构发现」或「影响力评估」；
把引用边直接映射成**工程落地缺口**的工作很少，且需要一份跨领域语料——
30 站 × 10k 的语料 + 全可追溯 DOI 正好是这份语料。

### 方向二：弱监督标签的可靠性标定（LF Calibration）

**已实现过半**：把 Snorkel 的「可靠性估计」往上抬一层——
**不去估计 LF 输出标签的可靠性，而去估计 LF 特征本身的可靠性**。

实测支撑（跨样本稳定，非过拟合）：
- `precision agriculture` 在标题出现 943 次，只有 13 篇真被 OpenAlex 指派该概念
  → 逐标签 precision 可测且可跨样本比对（22.5k 标定 / 7.5k 留一：agriculture 0.481→0.375、cancer 0.547→0.489）。
- 标定后只保留 `support≥50 且 precision≥0.2` 的 245 个标签（从 2,200 个），
  整体准确率 **0.061 → 0.375**，`lf_corpus_vocab` 权重升到全场第 2。
- 作用域规则也是实测出来的：只匹配标题 0.0823 > 标题+摘要 0.0598 > 全量 0.0453，
  且标题前 80 字与全标题 precision 完全相同 → 决定「只扫标题前 80 字」。

**可发表的点**：先标定特征、再谈 LF 加权，这条方法论路径在弱监督文献里是空的。

### 方向三：跨域错路由作为语料质量基准（Cross-domain Misrouting Benchmark）

**已有产物**：`export-misroute-review.js` 导出 141,459 个有摘要实体的候选池
（cross-domain 40,160 / mixed 37,298 / cross-cutting 15,809），
排序键经两轮修正（「跨簇越多越可疑」是错的，跨学科论文才是最典型误报；
正确信号是证据集中在单一正交簇），top500 人工可标注。

**可发表的点**：把「站点主题 ≠ 论文主题」定义成可量化的语料质量指标并做成公开 benchmark，
这类基准在检索/语料治理文献里缺位。

## 4. 硬骨头（攻克路径与代价，按 ROI 排序）

### 硬骨头 A：全量语义检索在 Workers 上是架构级不可行 —— 已量化，别再调参数

实测数据把这件事钉死了：

| 方案 | 体积 | 结论 |
|---|---|---|
| 单文件全量 300k 带摘要 | **≈ 150 MB** | Worker 内存 128MB，`JSON.parse` 直接 OOM |
| 当前单文件 18k（top-600/站） | 10.82 MB | 覆盖率 6%，已接近安全上限 |
| 全量按站分片 | **149.28 MB（30 片 / 300k 实体）** | 体积可行，但需要加载器 |

**结论**：Workers 单实例装不下全量，这是架构约束不是参数问题。
**攻克路径**：
1. 分片产物已经能生成（`--shards`，30 片 / 300k / 149.28MB），但**必须先有消费方才落盘**——
   没消费方就白占 Pages 配额（`_site` 已 654MB）。已加 `.gitignore` 防呆。
2. 分片托管到 **jsDelivr**（免费 CDN、不吃 Pages 配额、单文件 5MB 远低于其 20MB 限制；
   本项目公开 GitHub 仓库，天然可 CDN 化），Worker 按 `sites` 参数按需加载 + 时间预算渐进加载。
3. 该改动需要重写 `api-guard/worker.js` 的索引加载函数（约 60 行），
   并保证任何失败都**回退到现有单文件索引**——不要让「优雅降级」变成生产静默故障。
4. 更彻底的方案是把检索迁到向量库（Farui / pgvector），代价是引入运维与成本。

**本轮不做**：无消费方 + 改 Worker 要重部署 CF 生产，风险收益比不成立。代码与体积已量化，随时可接。

### 硬骨头 B：引用图谱（进行中）

已跑通：260,689 个 DOI → 5,214 批批量查询，`select=referenced_works,abstract_inverted_index`
验证可行；摘要顺带回填。当前 8 并发全量抓取中（进度写 `state/openalex-citation-cursor.json`，每 20 批落一次，
可随时中断续跑）。设计上刻意只落「跨站引用边 + 计数」，域内引用不成边——
因为域内引用单域平台都能查，**跨站引用边才是别人做不到的部分**。

体积预算已算过：OpenAlex 原始 payload 平均 ~4KB/条 × 276k ≈ 1.1GB，**绝不可落库**，
所以只落 id 映射 + 引用计数 + 跨站边（每实体限 12 条）。

### 硬骨头 C：语料增长已停滞

30 站 × 10,000 已满容，摘要回填缺口 0，每小时新增 0。
要继续长数据，只有引入新源。worker.js 的 404 提示里列了 3 个学术端点
（`/v1/academic/entities|pubmed|crossref`），对应 `data/academic-entities.json` 等 4 个数据集
在 `build-site.mjs` 的复制清单里**有名字、没产物**——也就是三端点天天 404。
**这是本轮最该补的增长点**：跑通 OpenAlex 扩库（`pipeline-openalex-expand.js` 缺失，需重建），
顺带把 3 个 404 端点救活。

## 5. 市场壁垒（诚实评估）

### 5.1 现在不算壁垒的东西

- **数据量**：30 万实体听起来大，但源是 OpenAlex/Crossref/GitHub 等开放 API，
  任何人都能抓一份。**复制成本 ≈ 0**，不构成壁垒。
- **「我们有 14 个/30 个站」**：站点本身是内容编排，不是资产。
- **语义检索**：覆盖率 6%，连自己都 beats 不了全量，短期内不是卖点。

### 5.2 真正能构成壁垒的三件事

1. **跨域整合视图**（唯一可持续的差异化）
   单域检索谁都能做；把 30 个学科的引文流织成一张图、并持续维护 schema 一致性，
   需要持续运维投入。今天修的护栏自锁 bug 就是这类资产的具体形态——
   **别人重新搭一遍，会踩一模一样的坑**：多写入者 + 跨 schema 基线 + 护栏自锁。
   这类「踩过的坑本身」是 Thesis 资产，且不可被一次 git clone 复制，只能在长期运维中累积。

2. **可追溯的结构化输出**（ToB 付钱的理由）
   每条实体都带 DOI / URL / 来源站 / `publishedDate` / `confidence`，外部可独立核验。
   对做 RAG 的团队，这是「能作为 grounding 源」与「只能当灵感参考」的区别，值得付费。

3. **运维正确性**（稳定性即卖点）
   CI 门禁前移到编译期、护栏基线隔离、ETL 幂等。消费者接的是生产数据，
   一天静默吐错数据比一天挂掉更致命。

### 5.3 当前最大的缺口（比数据还大）

**有数据、没商业闭环。** 具体：
- API 端点 9 个全活，但**消费者无法自助接入**——`openapi.yaml` 与
  `docs/consumer-onboarding.md` 此前在仓库里不存在（本轮已补）；
- 定价页只在构建产物 `_site/pricing.html`，没有对外可结算路径；
- 3 个学术端点 404 会直接劝退首批 TA 型用户；
- 摘要已填满、实体已满容，**数据侧再投入 ROI 低**，投入该转向「让消费者用起来」。

**建议的下一步排序**：① 救活 3 个学术端点（跑扩库）→ ② 把 onboarding 文档推到对外域
→ ③ 定价页与支付闭环落地 → ④ 引用图谱产出后，把它做成 Pro 档的第一杀手锏
（「跨站引用缺口」不是任何单域平台能给你的）。

# GeneTech 知识引擎 · 地基体检与硬骨头攻坚方案（2026-10-16）

> 本轮性质：**不打分的体检**。前八轮回答的是"建什么、建到哪"；本轮只回答一件事——**这栋楼的地基承不承得住继续往上盖**。
> 方法：全仓扫描 + 逐项实测（29.4 万实体字段级统计、图/边结构解析、测试资产清点、幂等与告警代码级核验、依赖与产物状态核对）。**每一个结论都带实测数字，没有"应该是"。**
> 立场：内部工程决策。宁可现在难看，不要将来塌。

## 1. 第一硬骨头：数据地基（最贵、最慢、但最该先做）

### 1.1 空值不是"缺字段"，是"缺载荷"
字段存在率 100% 是假象——真正的问题是内容为空：
- abstract 空 **90,926 条（30.89%）**；
- tags 空 **103,887 条（35.30%）**——而 tags 是检索的**第二权重字段**（name 6 / tags 3）和跨域发现的主要输入；
- authors 空 72,752（24.72%）；两者皆无的实体 **84,513 条（28.7%）**。
- **有效载荷率仅 62.3%**，最差站 neuromorphic 只有 25.9%。

**这意味着**：现有 Recall@10=0.4126 里，有相当一部分不是"检索算法差"，而是**目标实体根本没有被检索算法看得见的字段**。先调算法是在给空房子刷墙。

**硬骨头动作（不是调 prompt，是补数据）**：
1. **abstract 回填换路线**：学术 API 三源回填已实测 0% 成功——放弃 API，改"**URL 直达 + 全文首段抽取**"（url 字段 0% 缺失，是现成的抓手）；本地小模型（Qwen3-4B）从落地页抽取摘要段落；目标 30 天内 abstract 缺失 ≤15%。
2. **tags 重建**：35% 无 tag 的实体，用 `adaptive-fields.mjs` 已有词表 + LLM 标注（distilabel 批处理）重建；tags 是后续 claim/假设/图谱的公共输入，**这一项不做，后面三层都缺原料**。
3. **建立"载荷完整度"分级**：把实体分为 L0（空壳）/L1（部分）/L2（完整），**对外数字、图谱构建、假设生成只吃 L1+**，并把这个分级写进 guards/quality 策略（现在 quality_tier A–E 只看单项指标，不看组合可用度）。

### 1.2 ID 命名空间不统一（会被未来放大十倍）
现状：`doi:` 205,099 / `oa:` 40,778 / `pmid:` 32,492 / `arxiv:` 15,789 / `epmc:` 71 / `ss:` 32 / `pp:` 1，**外加一批没有命名空间的裸 ID**（如 `arxiv-2607.29626v1`）。知识图谱的边直接引用了这类裸 ID。

**为什么是地基问题**：实体解析（Splink ER PoC）、claim 图、假设卡、外部引用都依赖 ID 稳定与可解析。现在**同一篇论文可能有 doi:/oa:/pmid: 三种 ID**，跨站重复 DOI 15,013 条就是证据。将来上 ER 与证据图时，这个债会以 O(n²) 的成本回来找你。

**硬骨头动作**：
1. 建立**规范实体 ID（canonical id）**：`genetech:<namespace>:<native>`，namespace 白名单化（doi/oa/pmid/arxiv/epmc/ss）；裸 ID 全部补前缀。
2. 建立 **ID 别名表（alias map）**：同一文献的 doi/oa/pmid/arxiv 多 ID 归一到 canonical id，作为**独立数据产物**交付（`data/identity-map.json`），ER 与 claim 图只用它。
3. **ID 稳定性契约测试**：CI 断言"同一输入重跑 ingest，ID 集合不变"（现在是隐式假设，没有任何测试保证）。这是"楼越高越不能动"的东西——详情 URL、外链、SEO、Agent 引用全靠它。

### 1.3 知识图谱：60% 是桩，且混入了非领域节点
- nodes 36,107 中 **stubNodes 21,751（60.2%）**；
- stations **56 个**——包含 `docs`、`data`、`guards`、`mcp-server`、`reports`、`tmp`、`sites` 等**非科学领域目录**，它们作为"站点节点"进了图谱；
- 边 99,725 条中 citation 27,868、cross_site 29,927、shared_tag 38,930；
- builtAt **2026-10-02**（14 天未重建）。

**后果**：跨域"发现"若基于这张图，会有相当比例的候选是基础设施目录之间的伪关系，或指向桩节点的空关系。

**硬骨头动作**：① 图谱构建只允许 `ALLOWED_SITES` 30 域参与，剔除 infra 目录；② stub 节点显式标记并在算法中降权/排除；③ 图谱重建入 CI 并断言 stub 比例 ≤30%；④ 图谱产物加 `builtAt + 输入数据版本`双戳（现在只有 builtAt，无法回答"这张图是哪批数据算出来的"）。

## 2. 第二硬骨头：正确性与契约地基（现在没有"地板"）

**实测**：44 个名字含 test 的文件里，绝大多数在 `.workbuddy/probe/`（一次性探针，如 `test-intel-v4.mjs`、`test-both-secrets.mjs`）或 `operations-plan/reports/daily-data-test-*.json`（日报数据，不是测试）。**真正带断言、能进 CI 的只有 `mcp-remote/_test_contract.mjs`（46 断言）**。根 `package.json` **没有 scripts**——即没有一个 `npm test` 入口。

**这解释了一个反复出现的模式**：前几轮发现的"声明完成 vs 实测可用"落差（npm 1.1.0、11/14 工具 404、TS 双请求、README 对不上代码）——**根因不是马虎，是没有任何东西在自动阻止它**。补一个门禁能修一处，修不了这一类。

**硬骨头动作（这是"地板"，必须先铺）**：
1. **统一测试入口**：根 `package.json` 增加 `scripts.test`，用 Node 内置 `node:test`（零依赖）跑 `tests/**`；把现有 46 断言契约测试纳入；CI 的 `mcp-gate`/`extra-ops` 增加 `npm test` 步骤，失败阻断。
2. **数据契约（schema）落地**：用 **zod 4**（mcp-server 已依赖）为 entities.json / index.json / citation-edges / KG 定义 schema，产出 `data/schemas/*.schema.json`；ingest 出口、sync-live 入口、MCP 工具出口三处强制校验。**现在 entities.json 没有任何 schema 校验**——30 站同构只是约定，不是约束。
3. **引用边改为对象结构**：现在是 `[doi, doi, siteA, siteB]` 四元数组，无字段名、无方向语义、无版本。改为 `{citing, cited, fromSite, toSite, resolvedAt, method}`，并提供一次性迁移脚本 + 旧格式兼容读取期（1 个 release）。
4. **不变量测试（invariant tests）**：把"地基级不变量"写成断言并在 CI 跑——
   - 每站 `index.json.totalEntities === entities.length`（当前 0 漂移，但没有测试守住）；
   - ID 全局唯一且带合法命名空间前缀；
   - KG 边不指向不存在的节点（当前实测 0 悬空，但需守住）；
   - search-index 的 coverage === 1 且 builtAt 与源数据时间戳一致；
   - 任一实体 url 可解析、publishedDate 可 `Date.parse`（当前 15 条不可解析）。
5. **属性测试（property-based）**：对检索与排序做随机输入不崩、不返回重复项、分页不重不漏的断言（`fast-check` 即可）。

## 3. 第三硬骨头：可靠性工程（现在靠人肉盯，不靠系统）

**实测缺口**：
- **幂等**：49 个管线脚本中**只有 8 个带 cursor**；retry/backoff 关键词只在 8 个文件出现。意味着大部分采集/加工脚本**中断即重头，或重跑即重复**。
- **原子写**：`pipeline-sync-live.js` 无 `tmp + rename` 模式——写一半崩溃会留下半截 entities.json，而该文件是线上 API 与 MCP 的数据源。
- **告警**：`monitor-flywheel-state.js` 里没有任何 webhook/alert/notify。**飞轮冻结 45 天这件事，是被人读报告发现的，不是被系统喊出来的**——这是最刺眼的一条。
- **并发**：cron 分散 4 个 workflow + 本地 scheduler 双轨，无全局锁。

**硬骨头动作**：
1. **统一写盘工具**：`lib/atomic-write.mjs`（写 tmp → fsync → rename），全仓 12 处"直接写 JSON"的调用点全部替换；CI 加"禁止直接写"的 lint 规则（grep 断言）。
2. **幂等三件套**：每个管线必须实现 (a) 输入指纹（source+query+参数哈希）、(b) 断点 cursor、(c) 写入前去重键；提供 `lib/pipeline-kit.mjs` 统一封装，新脚本强制继承。**目标：任一脚本连跑两次，产物字节一致。**
3. **重试预算与退避**：统一 `lib/fetch-with-retry.mjs`（指数退避 + 抖动 + 429/5xx 分类 + 每日配额预算），替换 8 个脚本里各自的手写逻辑；配额打满时**退出并告警**，而不是静默停（OpenAlex 12.7% 卡死就是这个失败模式）。
4. **告警通道（P0）**：`monitor-*.js` 接 GitHub Issue 自动开单（workflow 已有 `issues: write` 权限）+ Logpush 审计；SLO 定义：**飞轮 72 小时无新增实体 = 自动开 Issue**。这一条只要半天，但能防止下一个 45 天。
5. **单飞锁**：给 CI 的 4 个定时 workflow 加同一 concurrency group 与 `cancel-in-progress: false`，并在管线入口加文件锁，防止两个 pipeline 同时写同一站。

## 4. 第四硬骨头：为"楼更高"预留结构（现在不改，将来要拆楼）

前几轮方案里的向量层、claim 证据层、假设层都还没上，**现在是把承重结构预埋进去的最后窗口**——等数据涨到百万级再改 schema，成本是现在的十倍。

| 预留项 | 现在不做会怎样 | 现在做的最小动作 |
|---|---|---|
| **数据版本化** | 无法回答"这个结论基于哪批数据"；模型/假设无法回溯 | 每次 ingest 产出 immutable 快照 + `dataset-version` 戳；KG/citation/index 全部带输入版本 |
| **时间维度** | 引用图无时态，无法做"当时是否已知"的判断（科学发现的核心） | 边加 `firstSeenAt / validFrom / validTo`；实体保留 `addedAt/updatedAt` 双时态 |
| **来源分级** | 证据强度计算需要 source tier，现在 source 有 8 种但无等级 | `source` 增加 `tier`（peer-review / preprint / dataset / gray）与 `retrievedAt` |
| **存储格式** | 单站 entities.json 15MB、全量 518MB，加载 579ms 已靠分片勉强压住 | DuckDB/Parquet PoC 转正（已有工具链），实体表 + 边表分区；JSON 仅作发布格式 |
| **配额与成本** | 一旦上 LLM 抽取/向量化，成本会失控 | 建立 cost budget：每管线记录 tokens/请求数/耗时，超预算自动降级到规则法 |
| **多租户隔离** | Agent 生态开放后，单租户可拖垮全局 | key 维度配额（现在仅 KV 计数、per-isolate 失效）+ 单请求实体上限 |
| **可观测** | 出问题时只能读日志猜 | 结构化日志 + trace id 贯穿 ingest→加工→服务；`observe.mjs` 已预留 OTLP 接口，接上即可 |

## 5. 攻坚排序：先做什么（按"不做会翻倍"的利息排序）

## 6. 技术债利息表（这些现在不还，将来翻倍）

| 债 | 现在的成本 | 6 个月后成本 |
|---|---|---|
| ID 不统一 | 15,013 条重复 DOI | 加了 ER/claim/假设层后，每个产物都要重建映射 ×3 |
| 无 schema | 靠约定 | 百万实体 + 3 个新层后，任何字段变更都是全局迁移 |
| 无测试入口 | 靠人工复验 | 每加一层，回归面指数增长；幻觉/错误无法被 CI 拦 |
| 引边是数组 | 解析靠位置 | 一旦 Agent 外部消费，改结构 = 破坏性变更 |
| 图谱含 infra 站 | 伪关系噪声 | 假设生成会产出"docs 与 tmp 目录相关"级别的垃圾候选 |
| 无告警 | 45 天才被发现 | 系统越大，静默失败越久 |

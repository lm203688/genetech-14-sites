## 四、经验总结

### 4.1 关键认知

1. **地基 ≠ 表面**：KG 36,107 节点看似健康，但 44,148 缺时间戳、101/870 零引用对、25,682 条边用 4-tuple——表面繁荣下的地基问题
2. **原子写是硬前提**：F5 直接复用 F3 的 `atomicWriteJSON`，避免"边读边写"竞态
3. **不变量要早写**：F4 的 5 条不变量在 F5/F7 实施过程中作为门禁检查
4. **诚实标注优先级**：F7 遇到"2026 年未来戳"这种 bug 数据时，先诚实标注（validUntil=null）再修复，不掩盖问题
5. **双戳设计**：`resolvedAt`（系统记录时间）+ `firstSeenAt`（数据首次出现时间）+ `validUntil`（数据失效时间）三时间戳，为未来回溯提供基础

### 4.2 关键决策

| 决策 | 理由 |
|---|---|
| F1 用 GitHub Issues 而非外部 webhook | 零第三方依赖，100% 免费，官方标准集成 |
| F4 用 JSON Schema 而非 zod | 跨语言兼容（Node/Python/Rust），MCP 可直接消费 |
| F5 只处理 5 站（DOI/patent/gene/protein/chemical） | 收益最高（这些是主键型 ID），其他站保持现状 |
| F7 采用"诚实标注"策略 | 2026 年未来戳无法修复，先标记不掩盖，后续统一回填 |
| F8 保留 `method: "legacy"` | 标记历史遗留，便于后续清理 |

### 4.3 可复用模式

1. **cron + webhook + Issue**：任何"周期性检查 + 异常告警"场景都可复用
2. **AtomicWriteJSON**：所有 JSON 数据文件修改都应走这个 API
3. **schema + 不变量单测**：任何数据结构新增/修改都应配套 schema 和不变量
4. **identity_map**：任何跨站/跨命名空间 ID 关联都应通过别名表统一
5. **双戳 + source tier**：任何数据管道都应记录来源分级和时间戳

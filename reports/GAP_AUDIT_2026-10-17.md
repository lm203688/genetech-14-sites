## 2. A 类缺口：数字口径不一致（4 处，全部是"硬伤级"）

### A1 🚨 skill 数量有 **4 个互斥数字**

| 来源 | 数字 | 位置 |
|---|---|---|
| `skills/registry/` 实际文件 | **11** 个（不含 `schema.json`） | `ls skills/registry/` |
| `harness/manifest.json` | **11**（`skills.count = 11`，`implemented = 3`） | `harness/manifest.json` |
| `README.md` | **14** | README 全文出现 2 次 |
| `.well-known/agent.json` | **23** | `card["skills"]` 长度 |

**影响**：A2A Card 是对外身份声明，声明 23 个 skill 但注册表只有 11 个 → **外部 Agent 按 Card 调用会 12 个找不到**。这是 G1 的**直接阻断项**。

**补法**：
1. 确认"skill"与"MCP 工具"是同一概念还是不同概念（当前 Card 把 MCP 工具直接映射成 skill）。
2. 若是同一概念 → Card 的 `skills[]` 应该由 `skills/registry/*.json` **程序化生成**，不手写。
3. 若不同 → Card 需拆成 `skills[]`（11 个）+ `tools[]`（23 个）两个数组，并在 Card 里注明区别。

### A2 🚨 MCP 工具数在 README 里有 **4 个数字**

| 出现位置 | 数字 |
|---|---|
| README L139 | "第 **22** 个工具"（指 `agri_decision_path_report`） |
| README L242 | "暴露 **23** 个 agri 工具" |
| README 其它段落 | **20** / **14** |

**实际**：`mcp/server.py` 有 **23** 个 `_tool_*` 函数，`TOOLS` 注册表 **23** 条，A2A Card **23** 条。

**影响**：README 是对外门面，同一份文档里工具数出现 4 个数字，评审员第一眼就会质疑"这个项目自己都不知道自己有几个工具"。

**补法**：README 里所有工具数改为**引用单一源**（`harness/manifest.json` 的 `mcp.tool_count`），并加 CI 门禁 `scripts/check_readme_numbers.py`：README 中任何 `\d+ 个.*工具` 必须等于 manifest 的 `tool_count`。

### A3 🚨 CI 步骤数：CORE_OBJECTIVE 说 22 步，实际 **39 步**

**证据**：`grep -c "^\s*- name:" .github/workflows/ci.yml` = **41**

CORE_OBJECTIVE §九 写："CI（**22 步** × 3 Python 版本全绿）"。

**影响**：这个数字在"P0 完成 10/11"的总结里，属于**对外可信度声明**。22 vs 41 差 19 步，等于说"我做了 22 件事"实际做了 41 件——虽然是往多了做，但**数字不可信本身就是问题**。

**补法**：CORE_OBJECTIVE §九 改为"CI（**39 步** × 3 Python 版本全绿）"，并在 manifest 里加 `ci.step_count = 39` 由 CI 自动写入。

### A4 🚨 Schema 文件名：文档写 `env_recipe_schema.json`，实际是 `env_recipe.schema.json`

**证据**：
```
CORE_OBJECTIVE §10.1 不可进化区清单：schemas/env_recipe_schema.json   ← 文档
实际文件：                          schemas/env_recipe.schema.json     ← 磁盘
```

**影响**：`CORE_OBJECTIVE §10.1` 是**不可进化区**的权威清单，`engine/evolution.py` 启动时读这个清单做保护。如果清单里的路径错了，**保护逻辑可能静默跳过这个文件**（取决于 evolution.py 的实现是 `Path.exists()` 还是直接读）。

**验证**：`Path("schemas/env_recipe_schema.json").exists()` → **False**

**补法**：
1. 立即改 CORE_OBJECTIVE §10.1 的路径为 `schemas/env_recipe.schema.json`。
2. 在 `engine/evolution.py` 里加断言：不可进化区清单中每个路径必须 `exists()`，否则启动即报错。
3. CI 加一步 `check_immutable_zone_paths.py`。

## 3. B 类缺口：核心目标进度（G1/G2）

### B1 🚨 `feedback_log.json` **0 条**（G2 目标 ≥ 30）

**证据**：
```
data/feedback_log.json: 0.0 KB，0 条
```

**影响**：CORE_OBJECTIVE §二 G2 明确"`feedback_log` 真实回流（非 dry-run / 非合成）≥ 30 条"。当前 **0 条**。这意味着：
- 配方永远是"文献推导"，不是"实测校准"
- `bayes_calibration.py` / `federated_calibration.py` 两个模块**没有输入**
- G2 → G3 的路径完全堵死

**补法**（按优先级）：
1. **短期**（G1 前）：`agri_env_recipe` 返回值里加 `feedback_url` 字段，引导调用方回传（这是唯一能自然产生回流的入口）。
2. **中期**（G1 后）：写 `scripts/collect_feedback.py`，把外部调用方的 `outcome` 字段落盘到 `feedback_log.json`。
3. **验收**：`feedback_log.json` 里每条必须有 `source != "synthetic"` 且 `outcome` 非空。

### B2 🚨 `execution_log` 55 条**全部是 shadow，0 条真实执行**

**证据**：
```
条目数: 55
来源标记: source=shadow: 55 条 (100%)
          mode=shadow:   52 条
device_id: shadow_device_seed_001
params_unknown: true
```

**影响**：CORE_OBJECTIVE §六 L3 写"拿到第 1 条 `execution_log`"。实际有 55 条，但**没有一条是真实硬件执行**——全是 `shadow` 影子运行。这意味着：
- L3 执行闭环是"纸面闭环"
- `ControlAgent` 的补偿逻辑**从未被真实执行验证过**
- `verify_service.py` 的 Verify 能力**没有真实样本**

**补法**：
1. 在 `harness/manifest.json` 里把 `execution_log` 拆成 `shadow_count: 55` + `real_count: 0` 两个字段，**明确区分**，不再用一个总数掩盖。
2. 真实执行的最小可行路径：接一个 ESP32/树莓派 + 一个继电器 + 一个温湿度传感器，跑通"下发指令 → 设备执行 → 回传 actual_params"闭环（成本 < 300 元）。
3. 在 `execution_log.json` 的每条记录里强制 `source` 字段（`shadow` / `real` / `simulated`），CI 校验不得缺失。

### B3 🚨 `license=unknown` 152 条（法务红线未真正闭合）

**证据**：
```
sources 条目总数: 760
  source_license: 760 (100%)   ← 有字段
  data_quality:   760 (100%)   ← 有字段
  trial_location: 760 (100%)   ← 有字段

但 license 字段取值：
  'unknown': 152 条   ← 有问题
  'CC BY-NC-SA 3.0 IGO': 152
  'CC BY 4.0': 152
  'Public Domain (US Government)': 152
  'CC BY 3.0': 152
```

**影响**：CORE_OBJECTIVE §五 说"`sources[]` 每条必须补齐 `source_license`"。字段是补齐了，但 **152 条填的是 `unknown`**——这等于"我知道要填，但我不知道填什么，先填个 unknown 占位"。法务上 `unknown` 比不填更危险：**不填是"未声明"，填 unknown 是"已声明但无法确认"**。

**补法**：
1. 定位这 152 条 `license=unknown` 的具体文件和 `source` 名称。
2. 逐个查原始数据源的许可条款（FAO / USDA / WorldClim / SoilGrids 等各有明确条款）。
3. 确实查不到 → 从配方中**移除该 source**，而不是留 `unknown`。
4. CI 门禁：`license` 字段不允许为 `unknown` / 空字符串。

### B4 🟡 `measured` 数据只占 20%（152/760）

**证据**：

```
  modeled:      456 (60.0%)
  interpolated: 152 (20.0%)
  measured:     152 (20.0%)
```

**影响**：CORE_OBJECTIVE G2 的核心是"让配方从文献推导变为实测校准"。当前 `measured` 只占 20%，且这 20% 大概率也是**文献中的实测值**，不是本项目自己的实测。

**补法**：与 B1/B2 合并解决——真实执行 + 反馈回流才是 `measured` 的唯一来源。

### B5 🟡 `org_memory` / `long_term_memory` 几乎全空

**证据**（`harness/manifest.json`）：
```

org_memory.playbook_entries = 0
long_term_memory.memories = 3
long_term_memory.hyperedges = 0
```

**影响**：项目宣称"自进化"（`engine/rsi.py` + `evolution.py` + `flywheel.py`），但支撑自进化的记忆层几乎全空：
- `org_memory.trajectories = 0` → 组织级轨迹零条

1. 给所有 >30 天未更新的文档加头部标记：`> ⚠️ 本文档最后更新于 YYYY-MM-DD，可能已过期。权威口径见 docs/CORE_OBJECTIVE.md`
2. 明显冲突的文档（`项目方案一稿.md` / `项目完整方案-全球大农业v2.md` / `项目执行方案.md`）移到 `_archive/`，或加 `DEPRECATED` 前缀。

## 6. E 类缺口：Schema / 契约

### E1 🔴 `zone_note` 字段：Schema 有，152 份数据全无

**证据**：
```
Schema 声明字段: 16
实际数据字段: 15 种（152/152 全有）
Schema 有但数据没有: ['zone_note']
```

**影响**：要么是 schema 定义了没用上的字段（应该删），要么是数据缺了这个字段（应该补）。**两种可能都指向同一个问题：schema 与数据没有 CI 双向校验。**

**补法**：
1. 确认 `zone_note` 的设计意图。
2. 若需要 → 补 152 份数据；若不需要 → 从 schema 删除。
3. CI 加双向校验：`schema.properties - actual_fields == ∅` 且 `actual_fields - schema.properties == ∅`。

### E2 🔴 20+ 种 JSON 数据文件，只有 3 个 Schema

**证据**：
```
schemas/ 只有 3 个：
  env_recipe.schema.json
  execution_log.schema.json
  trust_mark.schema.json

data/ 下有 20+ 种 JSON：
  crop_adapt_db.json (222 KB)
  crop_phenology_extended.json
  device_catalog.json
  knowledge_graph.json (131 KB)
  linkage_protocol.schema.json
  long_term_memory.json
  preset_cities.json
  wofost_phenology_reference.json
  feedback_log.json
  ... 等
```

**影响**：`crop_adapt_db.json` 222 KB、`knowledge_graph.json` 131 KB——这两个是**核心数据资产**，但**没有 schema**。任何人改结构都不会被发现。

**补法**：优先给 `crop_adapt_db.json` 和 `knowledge_graph.json` 补 schema（这两个是下游所有计算的输入）。

### E3 🟡 `linkage_protocol.schema.json` 放在 `data/` 而不是 `schemas/`

**证据**：`data/linkage_protocol.schema.json` 存在，但 `schemas/` 里没有。

**补法**：移到 `schemas/`，或在 `data/` 里加 README 说明"这是数据文件不是 schema"。

## 7. F 类缺口：数据资产卫生

### F1 🟡 `data/_demo_runtime/` 560 个文件混在真实数据目录

**证据**：
```
data/_demo_runtime/: 560 文件
```

**影响**：`data/` 是"真实资产"目录，里面混了 560 个 demo 运行时文件。任何遍历 `data/**/*.json` 的脚本（如数据质量门禁）都会把 demo 数据当真实数据统计。

**补法**：移到 `data/_demo/`（已是下划线前缀，但需要确认所有遍历脚本都排除 `_` 前缀目录）。

### F2 🟡 4 个 `.bak_*` 备份文件未清理

**证据**：
```
crop_adapt_db.json.bak_20260923  (266 KB)
crop_adapt_db.json.bak_20261006  (266 KB)
crop_adapt_db.json.bak_before_calib (217 KB)
```

**影响**：不是大问题，但说明**没有备份策略**——备份是手动 `cp` 出来的，不是自动的。这与 H1（原子写）是同一个问题的两面。

**补法**：建立 `scripts/backup_data.py`，每次 `atomic_write` 前自动备份到 `data/.backups/YYYY-MM-DD/`，保留 7 天。

### F3 🟡 `data/snapshots/` 空目录

**证据**：`data/snapshots/: 0 文件`

**影响**：说明"快照"功能设计了但没用过。`recipe_scheduler` 依赖快照，但快照是空的。

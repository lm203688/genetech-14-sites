## 2. 本轮三个新发现（前五轮未覆盖）

### N1（P0，对外可证伪）：MCP "2026-07-28 规范"宣称不实

**实测过程**（可复现）：

```
$ cd mcp-server && PORT=3195 node src/http.mjs &

$ curl -s -X POST http://127.0.0.1:3195/mcp -H "Content-Type: application/json" \
    -H "Accept: application/json, text/event-stream" \
    -d '{"jsonrpc":"2.0","id":1,"method":"initialize",
        "params":{"protocolVersion":"2026-07-28","capabilities":{},"clientInfo":{"name":"t","version":"1"}}}'
→ {"result":{"protocolVersion":"2025-11-25", ...}}        # 服务端协商到 2025-11-25

$ curl -s -X POST http://127.0.0.1:3195/mcp -H "Content-Type: application/json" \
    -H "Accept: application/json, text/event-stream" \
    -H "MCP-Protocol-Version: 2026-07-28" \
    -d '{"jsonrpc":"2.0","id":3,"method":"tools/call","params":{"name":"citation_gaps","arguments":{}}}'
→ {"error":{"code":-32602,"message":"Invalid params: the MCP-Protocol-Version header names
   protocol revision 2026-07-28, but the request is missing the required
   per-request envelope key(s): _meta"}}

$ curl -s -X POST http://127.0.0.1:3195/mcp ... -H "MCP-Protocol-Version: 2025-11-25" （同 body）
→ {"result":{"content":[{"type":"text","text":"{\"mode\":\"gaps\",\"gaps\":[...]"}}}  # 正常返回
```

**三个事实**：
1. 服务端支持的最高协议版本是 **`2025-11-25`**，不是 2026-07-28（落后一个修订版）。
2. 客户端若声明 `2026-07-28`，SDK 直接以 `-32602` 拒绝——**缺 `_meta` per-request envelope**，即 2026-07-28 的"无状态核心 + 每请求自包含"要求**未实现**。
3. **SDK 本身无问题且已支持新版**：`@modelcontextprotocol/server` v2.3.1，作者 Anthropic PBC，npm registry 可查（`dist-tags.latest = 2.3.1`），包内含 2026-07-28 字样 606 处。**根因是服务端代码未升级，不是依赖问题。**

**为什么是 P0**：`mcp-server/package.json` 的 `description` 与 keyword `mcp-2026-07-28` 对外声称"实现 2026-07-28 规范（v2 无状态核心）"。一旦发布到 npm / Glama / Smithery，**任何评审或用户 10 秒即可证伪**。这正是本项目自己在 README「正确性门禁」定义的"**绿灯 ≠ 有效**"，也是 10-10 报告反复警告的"对外口径偏离模式化"的同型复发——且这次发生在**代码层的机器事实**上，比文档漂移更硬。

**修复方向**：二选一——(a) 把 description/keyword 改为如实声明 `2025-11-25`；(b) 实现 per-request `_meta` envelope 后真正支持 2026-07-28。**不能维持现状发布。**

### N2（P0，可用性）：MCP HTTP 模式首次 `tools/call` 冷启动 23.0 秒

**实测**：

```
$ time curl -s -X POST http://127.0.0.1:3195/mcp -H "Content-Type: application/json" \
    -H "Accept: application/json, text/event-stream" \
    -d '{"jsonrpc":"2.0","id":3,"method":"tools/call","params":{"name":"list_sites","arguments":{}}}'
event: message
data: {"result":{"content":[{"type":"text","text":"{\"count\": 30, ...
real	0m23.065s        ← 实测值
```

**根因**（读 `http.mjs` + `http-api.mjs`）：`http.mjs` 复用 `index.mjs` 的 server 与 tool handler；首次调用任一 tool 触发 `loadSites()`，**串行读取 30 个站点的 `entities.json`（每个 10–21 MB，合计约 450 MB JSON）并全量 `JSON.parse`**。缓存 TTL 5 分钟，之后每次冷启动重复一次。

**影响**：
- MCP 客户端普遍有 30–60s 超时；23s 已逼近危险区，真实网络 + 多客户端并发下更差。
- Phase 2 自述"health/init/tools/call 端到端 200"——**只验证连通性，未验证延迟**。同类"绿灯 ≠ 有效"：HTTP 200 不等于可用。
- `http.mjs` 启动日志 `tools=${existingServer._registeredTools?.size || '?'}` 实际打印为 `?`，佐证该文件未经真机验证。

**修复方向**：预加载 / 分片惰性加载（改用 `data/search-index/*.gz` 30 分片）/ 加 warmup 端点；**至少把 P95 首调延迟压到 <2s 并写入 CI 门禁**。

### N3（P1，度量失效）：新 leaderboard 的 100% 是无信息量的循环基准

**实测**（`eval/results-2026-10-12.json`）：

```
aggregate.queryCount   = 30
aggregate.avgRecall@10 = 1          ← 100%
aggregate.avgMrr       = 0.926
aggregate.avgNdcg@10   = 0.943
aggregate.missCount    = 0          ← 零漏检
aggregate.perfectCount = 30         ← 全部完美
```

**根因**（读 `eval/generate-queries.mjs` 的 `queryFor()`）：

```js
function queryFor(entity) {
  const parts = [];
  if (entity.name) parts.push(entity.name);
  if (Array.isArray(entity.tags)) parts.push(...entity.tags.slice(0, 3));
  if (entity.abstract) parts.push(entity.abstract.split(/\s+/).slice(0, 20).join(' '));
  return parts.join(' ').slice(0, 400);
}
```

**query 由目标实体自身的 name + tags + abstract 前 20 词拼成，答案就在 query 里。** 因此 `Recall@10 = 100%`、`missCount = 0` 是**由构造保证的恒等式**，不是检索质量。MRR 92.6% 也仅由并列排序的名次损耗造成，与"检索好不好"无关。

**为什么是 P1**：
- 该文件头注释已自陈"这不是'完美'的人工标注评测集"，Phase 2 总结也标注了"构造性基准"——**披露是有的**。
- 但 `eval/leaderboard-2026-10-12.html` 把 "Recall@10 = 100%" 作为指标展示，**读起来就是质量结论**。这正是本项目自己定义的"绿灯 ≠ 有效"。
- 更实质的代价：**它无法支撑"标准话语权"这条唯一低成本壁垒**——没有有效基准，`npx @genetech/data-mcp` 上线的意义也打折。

**修复方向**：改用**查询与答案不同源**的构造（用 tags 反查 name、用 abstract 中段短语、跨语言改写、人工标注子集 100–300 条），并引入多文档相关集（multi-relevant）以恢复 NDCG 区分度。
